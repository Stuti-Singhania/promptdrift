# Competitive landscape: public implementation evidence

**Accessed: 2026-10-01**, from the environment clock (`2026-10-01T15:00:21+05:30`). Sources below are pinned to the default-branch commits returned by GitHub during this review, not releases or promises about subsequent versions.

## Scope and interpretation

Independently inspected the recursive public trees of all twelve requested repositories, then relevant source, configuration, and workflow files. This assessment does not inherit claims from an earlier matrix. All requested repositories were accessible; two expose documentation/templates rather than an executable evaluation implementation in the inspected tree. No competitor code was copied into PromptDrift or executed, and no paid services or live model calls were tested. A workflow file demonstrates configuration, **not a successful CI run**.

**Unchanged-input drift** means observing fresh behavior over time while the resolved request and relevant configuration remain comparable. Running old/new prompts together is useful regression testing, but is not itself a historical drift check. An output difference is not necessarily a regression; unchanged captured inputs do not prove a provider-side cause if retrieval, tools, judge, routing, or other dependencies remain unobserved.

“Not established” below means not demonstrated by the cited implementation path—not proof that a capability is absent elsewhere. A hosted dependency's full capabilities are outside the scope of its example repository.

## Defensible opportunities for PromptDrift

These are **product/verification targets**, not claims of uniqueness or claims that PromptDrift already implements them.

1. **P0 — Make fresh unchanged-input checks an explicit, tested workflow.** Provide scheduled/manual canaries even when Git reports no prompt changes. Record whether each output was freshly generated, replayed, or cached, and keep “skipped” distinct from “passed.” Demonstrate detection with unchanged files and a deliberately changed mock provider. Arsenic baseline replay, heyllm canaries, and promptfoo's cache controls mean the opportunity is an understandable complete workflow—not inventing repeated evaluation.
2. **P0 — Separate observed facts from suspected causes.** Attach a versioned comparability manifest: resolved request hash, provider/endpoint/model identity, sampling settings, tool/retrieval hashes where available, evaluator version, and baseline/run IDs. Report “unchanged captured inputs; provider-side drift suspected” instead of asserting a provider update. Distinguish input/config/evaluator changes, transport failures, insufficient samples, and uncaptured context. Heyllm already provides A/B triage and judge-variation evidence; a defensible improvement must show narrower, auditable attribution rules and explicit unknowns.
3. **P0 — Ship a fail-closed CI reference that preserves evidence.** Test exit behavior for regression, missing/corrupt baseline, no cases, unavailable credentials, provider failure, and partial execution. Upload a machine-readable report even on failure, label offline demonstrations accurately, and test the actual documented command. The ecommerce `continue-on-error` and arsenic parser/documentation mismatch illustrate concrete integration risks; they do not establish that those projects cannot support stricter workflows.
4. **P1 — Tie reviewable baseline acceptance to immutable run evidence.** Keep observation history separate from the accepted baseline; support deliberate per-scenario promotion, parent baseline IDs, changed-contract warnings, and rollback. Require an explicit override for accepting known regressions. Arsenic already implements named/frozen baseline timelines, heyllm separates accepted baselines from observations, and promptfoo persists eval history. The opportunity is a coherent Git review/acceptance lifecycle, not “history nobody else has.”
5. **P1 — Make noise and privacy tradeoffs visible.** Offer bounded repeated sampling, sample counts, pass-rate/metric deltas, and an inconclusive state before strong attribution. Export useful reasons/hashes/metrics by default, with explicit opt-in raw evidence and a warning when hashes alone cannot reproduce a result. Test budgets and redaction on the actual CI artifact. Arsenic consistency runs and heyllm confidence/ledger logic are existing reference capabilities, not gaps to attribute to them.

**Positioning to validate:** “Git-reviewed, fresh behavioral drift checks with explicit comparability and auditable acceptance.” Avoid claiming that baselines, history, CI, repeat sampling, or unchanged-input triage are exclusive. The template and mocked-demo repositories are useful workflow references, but should not be used as evidence that executable competitors lack those features.
